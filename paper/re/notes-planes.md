# Scope "planes": the single paper plane over the teal canyon, and the flock of 32 planes in the blue canyon

All addresses are code32 offsets. "Tick" = 70.0018 Hz IRQ0 tick, "counter" = music counter [0x1ea8b]. Angles are
in sine-table units: 1024 = 360 degrees, `SIN(a) = sin_tab[a & 1023]` (65536*sin, 0x22479), `COS(a) = SIN(a+256)`.
16.16 = fixed point with 65536 = 1.0. Pixel coordinates refer to the original 320x200 frame.

Everything below was checked against the emulator, not only read (scripts in
`paper/re/models/planes/py/`, see section 9):
- canyon (0x2f24 + 0x3095): a Python model of the block renderer reproduces the back buffer bit-exactly (0 of 64000
  pixels differ) at t7000 (teal) and t9500 (blue);
- teal flight path: a per-tick model started from the part's initial noise table reproduces [0x6479] (position),
  the history index, the matrices and the plane offset exactly at the t6100 and t7000 snapshots;
- flock: a per-frame model (RNG included) started from the RNG state at the part entry reaches the t9500 snapshot
  state exactly (target, velocity, 32 plane records, camera matrix, camera position) after 327 frames;
- plane object: vertex transform/projection, face visibility, face colours, normals, neighbour links and static
  edge flags match the emulator for the teal plane (t7000) and all 32 flock planes (t9500).

## 3. The canyon renderer (both parts): 0x2f24 grid + 0x3095 8x8 blocks

### 3.1 Texture (teal part, 0x687a at 0x68a6..0x68e7, once at part start)

```c
u8 *base = tex;  tex += 0x10000;           // [0x1eddd]: the parts use base+0x10000, restore it on exit
for (i = 0; i < 65536; i++)                // done 4 bytes at a time: ((dw>>5)&0x07070707) + (rand()&0x02020202) + 0x8b8b8b8b
    tex[i] = 0x8b + ((base[i] >> 5) & 7) + (rand_bit_i ? 2 : 0);   // 139..148, each byte gets its own random bit
```
So a canyon texel is a "level" L = tex - 128 = 11 + (top 3 bits of the paper texture) + {0 or 2 at random}
(L = 11..20; the random +2 is per-texel grain, 50 % of texels). It is a 256x256 tile, nearest-texel, wrapping.

### 3.2 Ray grid — 0x2f24 (per frame)

The camera matrix rows (as stored, row-major) are the camera axes in world coordinates: r0 = screen right,
r1 = screen down, r2 = forward. Floats: M = [0x23a8] (= V/65536), C = [0x23cc..0x23d4], H = [0x23e4].
```c
for (j = 0; j <= 25; j++) for (i = 0; i <= 40; i++) {       // 26 rows x 41 columns, point (i,j) = pixel (8i, 8j)
    d = (-20.0 + i) * r0 + (-12.51 + j) * r1 + 28.0 * r2;     // incrementally: += r0 per column, += r1 per row (x87, 80-bit)
    t = (H - C.z) / d.z;  if (t < 0) t = (-H - C.z) / d.z;    // hit the plane z = +H or z = -H (whichever is in front)
    s = clamp(8 * (1024 - round(t)), 2048, 8192);             // shade, 8.8: row index s>>8 = 8..32 (fistp = round to nearest)
    grid[j][i].u = round((C.y + t * d.y) * -12.51);           // 8.8 texel coordinates
    grid[j][i].v = round((C.x + t * d.x) * -12.51);
}
```
- What it is: a raycast against two infinite parallel planes z = +H and z = -H (the camera is always between them).
  Both planes use the same mapping world (x, y) -> texture, so the ceiling is the floor's mirror image.
- Projection: pixel (px, py) <-> direction (px - 160)*r0 + (py - 100.08)*r1 + 224*r2: focal length 224 pixels,
  the same as the object projection (section 6.2); horizontal FOV 2*atan(160/224) = 71.1 degrees.
- Texture scale: one texel = 256/12.51 = 20.46 world units; a 256-texel tile = 5238 world units. u (texture row)
  comes from world y, v (texture column) from world x; the -12.51 makes both run backwards.
- t is the ray parameter for a direction whose forward component is 28, so the view depth is 28*t, and the
  fog term below is depth / 896.
- The value -12.51 at 0x23dc is used both as the vertical screen offset and as the texture scale (one constant).

### 3.3 Block interpolation — 0x3095 (per frame, edi = back buffer)

For each of the 40x25 blocks, the four corner grid points P00, P10 (right), P01 (below), P11 are interpolated
bilinearly, per channel c in {u, v, s} (exact integer behaviour, verified bit-exact):
```c
dx   = (P10.c - P00.c) >> 3;                                  // step per pixel along the top row
ddx  = ((P11.c - P01.c) - (P10.c - P00.c)) >> 6;              // change of that step per row
dy   = (P01.c - P00.c) >> 3;                                  // left edge step per row
row = P00.c;  step = dx;
for (y = 0; y < 8; y++) { cur = row;
    for (x = 0; x < 8; x++) { pixel = f(cur.u, cur.v, cur.s); cur += step; }
    row += dy;  step += ddx; }
pixel = shade[s >> 8][ tex[((u >> 8) & 255) * 256 + ((v >> 8) & 255)] ];   // u -> row (bh), v -> column (bl)
```
(The asm packs u (16 bits), v fraction and a guard byte into edx and carries into bl = v integer; the guard byte
starts at 0x80 so u wraps cleanly mod 256 texels. Shade fraction rides in the top byte of esi with carry into ch.)

### 3.4 Shading through the shade table (0x144b at init, verified)

```c
k' = (k <= 32) ? k : ((k-32) >> 1) + ((k-32) >> 3);                // rows 33..64: not used by these parts
shade[k][c] = (c < 64) ? max(0, c + 2*k' - 64)                       // grey ramp: 2 entries per step
                       : (c & 0xe0) + max(0, (c & 31) + k' - 32);    // 32-colour groups: 1 entry per step, floor at the group's entry 0
```
Row 32 is the identity. For the canyon (texel c = 128 + L, k = s>>8 in 8..32):
```
index = 128 + max(0, L - (32 - k)),  where 32 - k = clamp(t/32, 0, 24) = clamp(depth/896, 0, 24)
```
i.e. brightness = texel level minus a linear depth fog of one palette step per 896 world units, clamped at the
group's black entry 128. Everything with depth >= 17920 (t >= 640 for the brightest texel, 352 for the darkest)
is black: that is the black band along the horizon line where the two planes vanish. Only entries 128..148 occur.

### 3.5 Palettes: teal vs blue

- teal: 0x158e(0x681a) at the part start = base palette with entries 128..159 replaced by the 32 triples at
  0x681a, uploaded through the fade (0x15c0). Teal ramp: entry 128+n = black..(14,42,37) at n = 15..white.
- blue (flock): 0x15af = plain base palette, entries 128..159 = black..(11,43,63) at 143..white.
- The texture and the shading are identical; only the 32-entry ramp differs. Planes use the grey ramp 0..63 in both.

### 3.6 Shortcuts a high-resolution remake should evaluate exactly

1. **8x8 block interpolation** of (u, v, s): screen-linear interpolation of perspective quantities. Evaluate the ray
   per pixel: `t = (+-H - C.z)/d.z`, `u = -12.51*(C.y + t*d.y)/256`, `v = -12.51*(C.x + t*d.x)/256` (texels),
   `fog = clamp(28*t/896, 0, 24)`. Near the horizon line a block can have one corner at a huge t (millions of
   texels): the interpolated texture coordinates then sweep across many tiles inside the block, which is what makes
   the "hairy" streaks and 8-pixel steps along the black band. Per pixel these become ordinary minified texture.
2. **Fog quantisation**: the integer part of s selects one of 25 shade rows and the texel level is an integer, so
   the result is a 32-step palette ramp. A remake can use `ramp(L - fog)` with linear interpolation between ramp
   entries (continuous fog), clamped at entry 0 (black).
3. **Texture**: nearest-texel 256x256; at high resolution use bilinear/mip filtering of the *level* texture or
   regenerate it at higher resolution (the base paper texture is procedural, see the init notes; the +2 grain is
   per-texel noise with p = 0.5).
4. The ray directions are accumulated by repeated float32 additions (x87); exact per-pixel directions differ in
   the last bits only (visible only at t > 10^5, i.e. inside the black band).

A per-pixel float version of the above (exact formulas, continuous fog) rendered from the t7000 and t9500
snapshots looks the same as the original apart from the block steps (scratch `exact_7000.png`, `exact_9500.png`).

### 4.2 Wave noise (0x2756, 0x26d0, 0x67b9)

```c
struct Wave { i32 phase, amp, speed; } W[72];          // [0x1edd5]
void init_waves(int scale /*ebx=300*/) {               // 0x2756
    for (n = 0; n < 72; n++) { W[n].phase = rand(); W[n].amp = (rand() & 0x3ff) + 0x100;          // 256..1279
                               W[n].speed = (((rand() & 0xff) - 0x80) * scale) >> 8; }            // -150..148
}
void waves_advance(void) { for (n = 0; n < 72; n++) W[n].phase += W[n].speed; }   // 0x26d0, twice per tick
int noise4(const Wave *w) {                            // 0x67b9: uses w[0], w[2], w[4], w[6]
    int sum = 0;
    for (int cl = 4; cl >= 1; cl--, w += 2) {
        i32 a = ((i32)((u32)w->phase << (cl + 1)) >> 2) + 0x8000000;   // 8.8 index into the 1024-entry table
        int i = (a >> 8) & 1023, f = a & 255;
        int s = (sin_tab[(i + 1) & 1023] * f + sin_tab[i] * (f ^ 255)) >> 8;   // lerp, weights f and 255-f
        sum += (s * w->amp) >> cl;
    }
    return sum >> 15;
}
```
Float equivalent (to within 1/256 and the truncations):
`noise4 = sum over cl=1..4 of (amp_cl / 2^(cl-1)) * sin(2*pi * 2^(cl-1) * phase_cl / 2^18)`
with entry w[0] -> cl=4 (8x frequency, amp/8), w[2] -> cl=3, w[4] -> cl=2, w[6] -> cl=1 (base frequency, full amp).
Range +-2398. Each phase advances 2*speed per tick: the base octave has a period of 2^18/(2*|speed|) ticks
(>= 874 ticks = 12.5 s), the top octave 8x faster. Only W[0..22] even entries are used (yaw 0,2,4,6; pitch 8..14;
roll 16..22); the rest of the 72 are computed but unused.

Initial values in the reference run (W[n] = {phase, amp, speed} right after 0x2756 at tick 6018, n = 0,2,...,22) —
with these, the per-tick model below reproduces the capture's flight path exactly:
```

```

### 4.3 Flight path, camera and plane — 0x64f1 (per tick; also 28x pre-roll)

Matrix helpers (16.16, row-major m[3*r+c]; 0xae2 `out = A*B` with each product `(a*b)>>16` truncated):
```
0xbaa RotX(a) = [[1,0,0],[0,c,-s],[0,s,c]]      0xbed RotY(a) = [[c,0,s],[0,1,0],[-s,0,c]]
0xc30 RotZ(a) = [[c,-s,0],[s,c,0],[0,0,1]]      0xb1f(a=eax, b=ebx) = RotX(a) * [[cb,0,-sb],[0,1,0],[sb,0,cb]]
```
```c
i32 pos[3];                       // [0x6479], 22.10 world units; pos[2] is never changed (0)
int k = 900;                      // [0x4843] plane offset, exe data
void path_step(void)              // 0x64f1
{
    int N1 = noise4(&W[0]), N2 = noise4(&W[8]), N3 = noise4(&W[16]);
    int yaw = (N1 * 5) >> 3, pitch = (N2 >> 6) + 25, roll = N3 + 0x180;
    R = RotZ(roll) * RotX(pitch) * RotY(yaw) * RotX(256);       // [0x6455]; rows = right, down, forward
    pos.x += (R[2][0] * 3) >> 1;  pos.y += (R[2][1] * 3) >> 1;  // forward*1.5 per tick (z ignored)
    h = &hist[idx];                                             // 28-entry ring [0x2449d], idx [0x24499] (starts 0, buffer zeroed at init)
    cam = { h->x >> 10, h->y >> 10, N2 >> 11 };                 // [0x1ea9d..] ints and [0x23cc..] floats
    V = h->m;                                                   // [0x1e468] (int) and [0x23a8] = V/65536 (float, 0x679b)
    *h = { pos.x, pos.y, R };  idx = (idx + 1) % 28;
    plane.m = transpose(R);                                     // object matrix (model -> world), current attitude
    plane.pos[c] = (pos[c] >> 10) + ((V[0][c] * k) >> 15) - ((V[2][c] * k) >> 15);   // c = x,y,z
    if (counter > 0x2f0 && k != 0) k -= 2;                      // after counter 752: -2 per tick (ticks 6429..6878)
}
```
- Heading: forward = (-cos(p) sin(y), cos(p) cos(y), -sin(p)) in world; the canyon planes are z = +-1000, so the
  camera flies horizontally between them at z = N2>>11 (-2..1, i.e. the middle). Yaw = 5/8 of the noise (+-1499,
  wanders over +-1.5 turns), pitch = 25 +- 37 units (-4..22 degrees, nose down; only an attitude, the path is
  flat), roll = 384 + noise (+-2.3 turns) — the roll is what turns the two planes into walls/floor/ceiling.
- Speed: 1.5*65536/1024 = 96*cos(pitch) world units per tick = ~6700 units/s, about 1.3 texture tiles per second.
- Camera = the path state (position and attitude) 28 ticks earlier (0.4 s behind). The plane at k = 0 is the
  current path state, ~2690 units ahead of the camera, seen from behind; its attitude relative to the camera is
  R(now-28)*R(now)^T, so it banks/pitches on screen when the path curves.
- k: the plane is displaced by 2k*(camera right - camera forward) world units (k = 900: 1800 right, 1800 back).
  From counter 752 (tick 6429) k falls by 2 per tick to 0 at tick 6878; the plane enters from the right and passes
  close to the camera (first pixels at tick 6537, biggest around 6640), then settles ahead.
- Pre-roll: 28 path steps with unchanged phases at the part start, so the camera starts 28 steps behind the plane
  on a straight line; then one path step per tick, each after two phase advances.
- In the reference run the path reaches |x|,|y| up to 41000 world units.

### 4.4 Time base (teal)

All animation is **per tick** (IRQ callback, 70.0018 Hz): wave phases (+2*speed), path step (position, attitude,
camera = 28-tick delayed copy, camera z), plane offset k (from counter 752), peel progress. [0x217d9] and
[0x1edc1] are also counted per tick but not read by this part. The main loop only renders the current state
(frame-rate independent). Measured: 1.43 frames per tick during the plane section, 1.35 during the peel, at
1.5M instructions per tick, i.e. ~1.05M (1.11M during the peel) emulated instructions per frame (~100 fps).
Note: the IRQ can change the state between 0x2f24 (canyon) and 0x3fb3 (plane) in the same frame, so the
original occasionally draws the plane one tick ahead of the canyon; a remake should use one state per frame
(and may interpolate between ticks for display rates above 70 Hz).

## 5. The flock part (0x388b)

### 5.1 Set-up and main loop

```c
void flock_part(void)                                  // 0x388b, [0x1ea8f] = 0x500
{
    set_palette_base();                                // 0x15af (blue ramp)
    V = 0xb1f(0x100, 0) = RotX(256) = [[1,0,0],[0,0,-1],[0,1,0]];   // right +x, down -z, forward +y
    cam = (-10000, 0, 0);  Cf = (0, 0, 0);  H = 2000.0;               // float matrix [0x23a8] is not reset: the first
                                                       // frame's canyon uses the teal part's last camera (drawn at fade level ~0)
    flock_setup();                                     // 0x33d0
    clear VGA;  tex += 0x10000;                        // canyon texture left by the teal part
    fade_target = 0x8000;  callback = 0x3884;          // fade-in at the current step (300 per tick: 110 ticks)
    tickc = 0;  flock_steer();                         // 0x342f once extra (first frame: two steering calls)
    do {
        flock_steer();  tickc = 0;                     // 0x342f   ([0x1edc1] = 0, never read)
        canyon_grid();  key_check();  canyon_blocks(backbuf);   // 0x2f24, 0x7a64, 0x3095
        flock_move_draw();                             // 0x3618 (+ 0x37af camera, 0x43df draw)
        copy backbuf -> VGA;
        if (counter >= 0x500) { fade_target = 0; fade_step = 300; }
    } while (fade_level != 0);                         // 0x397e: THE SKIP BUG (NOTES.md): level only rises in the IRQ;
                                                       // if set-up + first frame finish within one tick, the part is skipped
    callback = 0;  tex -= 0x10000;
}
struct Rec { Object *obj; i32 x, y, z; i32 yaw, pitch, speed, pad; };   // [0x33c0], 32 x 0x20; pos in 20.12 world
void flock_setup(void)                                 // 0x33d0
{
    (target.x, target.y, target.z) = rnd3(63);         // [0x3390]  (velocity [0x33a8] = 0 from the exe)
    for (n = 0; n < 32; n++) {
        rec[n].obj = load_object(0x1878b, base_colour 0x1e);   // own copy, matrix = identity (nose along +z)
        (a, b, c) = rnd3(0x3ff);
        rec[n].x = a << 11; rec[n].y = b << 11; rec[n].z = c << 10;   // +-511, +-511, +-255 world units
        rec[n].yaw = rec[n].pitch = rec[n].speed = 0;
    }
}
```
RNG (0xaa2): additive lagged Fibonacci on 64 dwords at 0x9a0 with byte indices i = [0xaa0], j = [0xaa1]
(j = i + 34 mod 64): `x = T[i] + T[j]; T[j] = x; i = (i+1)&63; j = (j+1)&63; return x;`, i.e.
x(n) = x(n-64) + x(n-34) mod 2^32. Helpers: `rnd(m)` (0x377f) = `x = rand(); v = x & m; return (x & 0x10000) ? -v : v;`
(-m..m, 0 twice as likely). `rnd3(m)` (0x3793) calls rnd three times, r1, r2, r3, and returns them in the order
**(r3, r1, r2)** (eax = r3, then pop r1, pop r2) — order matters only for bit-exact replay. During this part only
0x342f/0x377f call the RNG (checked), so the flock is a pure function of the RNG state at entry and the frame count.

### 5.2 Target point and steering — 0x342f (per frame)

```c
void flock_steer(void)
{
    (a, b, c) = rnd3(1);  v = vel + (a, b, c);         // random walk of the velocity (x gets r3, y r1, z r2)
    if ((rand() & 63) == 0) v = rnd3(7);               // 1 in 64: new random velocity
    v = clamp(v, -7, 7) per axis;  vel = v;
    prev = target;                                     // [0x339c], unused
    for each axis (limit 450, 450, 14):                // bounce: reverse, and stay put this frame
        n = target + vel;  if (n < -limit || n > limit) { vel = -vel; n += vel; }  target = n;
    T = target * 16;                                   // world units: x,y in +-7200, z in +-224
    for (n = 0; n < 32; n++) {
        m = rec[n].obj->m;  p = rec[n].obj->pos;       // pos = world position (rec.x >> 12 ...) from the last move
        d = (T - p) >> 4;                              // per axis, arithmetic shift
        rec[n].yaw   = -(( (rnd(63) << 16) + m[0][0]*d.x + m[1][0]*d.y + m[2][0]*d.z ) >> 20);  // column 0 = local x
        rec[n].pitch = -(( (rnd(63) << 16) + m[0][1]*d.x + m[1][1]*d.y + m[2][1]*d.z ) >> 20);  // column 1 = local y
        rec[n].speed += 12 + rnd(3);                   // 9..15, consumed (and zeroed) by the next move
    }
    sway_x += 0x64;  sway_y += 0x8f;  sway_z -= 0x48;  // [0x33c4], [0x33cc], [0x33c8]
}
```
In real terms: turn = -(local offset to the target / 256 + rnd(63)/16) angle units, i.e. proportional steering
with gain 1/256 unit per world unit of lateral offset (no limit), plus a jitter of up to +-3.9 units (+-1.4 deg)
per axis and frame. The jitter is added before the shift, so the result is floor((jitter*16 + offset)/256).

### 5.3 Turn, move, draw, camera — 0x3618 + 0x37af (per frame)

```c
void flock_move_draw(void)
{
    sum = 0;
    for (n = 0; n < 32; n++) {
        Object *o = rec[n].obj;
        o->m = o->m * 0xb1f(rec[n].pitch, rec[n].yaw); // local rotation (right-multiplied): pitch about local x, yaw about local y
        s = rec[n].speed;  rec[n].speed = 0;
        rec[n].xyz += s * column2(o->m);               // forward = column 2 (model +z), 16.16 * s -> 20.12
        o->pos = rec[n].xyz >> 12;  sum += o->pos;     // world units
        object_transform(o);                           // 0x3fb3 with the camera of the previous frame
    }
    c = sum >> 5;                                      // flock centre
    c.x -= cam.x + cam.y + cam.z;                      // BUG (0x36f8..0x3713): all three camera coordinates are
                                                       // subtracted from x; y and z stay absolute
    cam = { SIN(sway_x >> 4) >> 5, SIN(sway_y >> 4) >> 6, SIN(sway_z >> 4) >> 6 };  // +-2048, +-1024, +-1024
    camera_track(c);                                   // 0x37af
    mode = 0;  draw_buckets();                         // 0x43df: all 32 planes depth-sorted together
}
void camera_track(c)                                   // 0x37af
{
    c >>= 8;                                           // per axis
    b = (V[0][0]*c.x + V[0][1]*c.y + V[0][2]*c.z) >> 15;   // = local x / 128 (world units -> angle units)
    a = (V[1][0]*c.x + V[1][1]*c.y + V[1][2]*c.z) >> 15;   // = local y / 128
    V = RotZ(2) * 0xb1f(a, b) * V;                     // turn towards the centre, then roll 2 units (0.70 deg)
    float matrix = V / 65536;  float cam = cam;        // for the next frame's 0x2f24
}
```
The steering turns the forward axis towards the target: new forward (local) = (-sin b, -sin a cos b, cos a cos b)
with b = yaw, a = pitch, both negative of the target offset. Roll is never controlled, so each plane's roll drifts.
The camera turns towards (the slightly wrong) flock centre with gain 1/128 angle unit per world unit of lateral
offset per frame and rolls by a constant 2 units per frame.

### 5.4 Time base (flock): everything is per drawn frame

| variable | step per frame | at 34.3 steps/s |
|---|---|---|
| target velocity | += rnd(1) per axis, 1/64 chance of a new rnd(7) vector, clamp +-7 (x16 = world) | |
| target position [0x3390] | += velocity, bounded +-450/+-450/+-14 (x16 world) | up to 112 world units/frame/axis |
| plane turn | yaw/pitch recomputed from the target offset + jitter | |
| plane speed | s = 12 + rnd(3) = 9..15 per frame; move = s * forward(16.16) in 20.12 = 16*s = 144..240 world units | ~6600 world units/s |
| sway angles | +0x64, +0x8f, -0x48 (table index = angle >> 4) | periods 163.8, 114.6, 227.6 frames = 4.8, 3.3, 6.6 s |
| camera roll | 2 units = 0.703 deg | one turn per 512 frames = 14.9 s |
| camera turn to centre | proportional, gain 1/128 unit per world unit | |

The callback 0x3884 only counts ticks into [0x1edc1], which the loop zeroes every frame and never reads. The
reference capture (`--plane-budget 750000`) runs at 0.49 frames per tick = 34.3 fps on average (33–37 fps in
215-tick windows, depending on how many plane faces are visible), i.e. ~1.53M emulated instructions per frame
(at the default 1.5M per tick the emulator draws 68 fps and the original would skip the part). The exact frame
schedule of the capture is the 5th column of full.ticks for ticks 8818–10967 (it sums to 329 for 8818..9499;
that count includes the greetings' last frames in tick 8818 and the frame in progress, and the t9500 snapshot
is reached after 327 complete flock frames). Step the flock at ~34.3 Hz; for smooth display
at higher rates interpolate positions/orientations between steps.

## 6. The plane object (0x39a4 loader, 0x3eeb set-up, 0x3fb3 transform, 0x43df draw)

### 6.1 Models (static data)

Format at the source address: `u8 nverts, u8 nfaces, nverts x (s8 x, s8 y, s8 z), nfaces x (u8 v0, v1, v2, u8 attr)`;
vertices are multiplied by 8 on load (world units); attr bits 0..2 = static outline flags for edges v0v1, v1v2,
v2v0; attr bits 4..7 = colour index into 0x3a89 (+ the base colour passed in al: teal 0x20, flock 0x1e).
Model axes: x right, y down, z forward (nose at z = 0, tail at z = -100). Both planes use colour index 0, so the
base colour is 16 + 0x20 = 48 (teal) or 16 + 0x1e = 46 (flock), in the grey ramp.

Flock plane (0x1878b): the classic dart, 6 triangles each stored twice with opposite winding (two-sided):
```
v0 (0,0,0) nose, v1 (-25,-10,-100) left wing tip, v2 (-5,-10,-100), v3 (0,0,-100) keel at the tail,
v4 (5,-10,-100), v5 (25,-10,-100) right wing tip, v6 (-1,-10,-30), v7 (1,-10,-30)
faces (v0,v1,v2,attr): (2,6,1,7) (5,7,4,7) (0,6,2,3) (3,0,2,5) (7,0,4,5) (4,0,3,6)
                       (1,6,2,7) (4,7,5,7) (2,6,0,3) (2,0,3,6) (4,0,7,6) (3,0,4,5)
```
(wings 1-2-6 and 4-5-7 lie flat at y = -10; 0-2-6 / 0-4-7 are the inner wing halves; 0-2-3 / 0-3-4 the keel.)
Wingspan 400, length 800, keel depth 80 world units.

Teal plane (0x187d5): the same 8 corner vertices (v0..v7 identical) plus 48 vertices that subdivide each of the
6 triangles into 9 small ones around inner points; each side has its own copy of the inner points (v8..v31 for one
winding, v32..v55 for the other). The wing triangles stay flat; the inner points of the keel and inner-wing
triangles are pushed slightly out of plane, so those sides break into facets with different shades ("folded
paper"). 108 faces = 54 per winding. The data's static outline flags are set on edges that lie on the original
6-triangle borders (not on all of them; the crease rule in 6.2 adds a few more); the subdividing edges are only
outlined as silhouettes. Read it from the exe (602 bytes).

### 6.2 Load / set-up (0x39a4, 0x3dc0, 0x3eeb; at part start)

Object struct (0x7c bytes + vertex and face arrays): +0 m[9] model->world (16.16, starts as identity),
+0x24 W[9] = V*m, +0x48 pos[3] world, +0x54 view translation[3] (16.16), +0x60 light[3] (object space, |L| = 200),
+0x6c nverts, +0x70 nfaces, +0x74 faces, +0x78 vertices. Vertex 0x24 bytes: +0 xyz (model*8), +0xc/+0x10/+0x14
view X/Y/Z (16.16), +0x18/+0x1c screen x/y (1/32 pixel). Face 0x4c bytes: +0/4/8 vertex pointers, +0xc/+0x10/+0x14
neighbour face across edge v0v1/v1v2/v2v0, +0x18 depth-list link, +0x1c/+0x20 mode-2 extras (unused here),
+0x1d flags (bit 7 hidden, bits 0..2 dynamic outline, bits 3..5 static outline), +0x1e base colour,
+0x1f drawn colour, +0x24 normal[3].
```c
normal (0x3dc0): e1 = B - A, e2 = B - C;  n = e1 x e2;  len = round(sqrt(n.n)) (or 1);  n = trunc((n << 8) / len);   // |n| = 256
neighbour (0x3f37) for edge (a -> b) of face F: the first face G != F in list order containing b -> a (by vertex
    pointer); if none: G = F. Static flag for that edge |= (G found && n_F . n_G <= 10000)   // >= 81.2 deg crease
```
Static outline flags = data flags | crease flags. Where the neighbour found is the reversed twin of a two-sided
face, n_F . n_G = -65536 and the crease rule always fires (e.g. all edges of the flock plane's faces 6..11).

### 6.3 Transform, cull, shade, bucket — 0x3fb3 (per frame)

```c
W = V * o->m;                                                    // 0xae2
T = V * (o->pos - cam);                                          // 16.16 (no shift): view-space translation
L = o->m^T * (LIGHT - o->pos) >> 16;  L *= 200 / |L|;  round;    // object-space vector to the light point (float sqrt)
for each vertex v:  Z = W[2].v + T.z;                            // 16.16 world
    if (Z > 25.0) { f = 0xe00000 / (Z >> 16);                    // 224*65536 / Z_int (truncating idiv)
        X = W[0].v + T.x;  sx = ((X * f) >> 27) + 0x1400;        // 1/32 pixel: 160 + 224 * X/Z
        Y = W[1].v + T.y;  sy = ((Y * f) >> 27) + 0xc80; }       // 100 + 224 * Y/Z
for each face: visible = all 3 Z > 25.0 && (sy2-sy0)*(sx1-sx0) > (sx2-sx0)*(sy1-sy0);
    if visible: colour = base + ((n . L) >> 12);                 // base +- 12 (n.L <= 256*200): 36..60 / 34..58
for each visible face:  flags bits 0..2 = (neighbour across that edge is hidden);
    key = clamp(((Z0 + Z1 + Z2 (integer world)) - 1200) >> shift, 0, 1023);  push face on bucket[key];
    // shift = byte at 0x42ac: 3 in the teal part, 6 in the flock part
```
- Shading: flat, one colour per face, linear in cos(angle to the light point), two-sided, no clamp:
  `index = base + floor(12.5 * cos)` on the grey ramp (index c ~ grey (c-1)/63). The light is a point at
  (-1300, 100, -2500) in world, so the light direction depends on where the plane is (different for every
  flock plane, and changing along the teal path).
- **Overflow in the original** (teal part only): `m^T * L` is computed in 32-bit with |L| up to ~43000 when the
  path is far from the origin; the sums wrap and the light direction is wrong (mostly by 110..135 degrees, i.e.
  the shading roughly inverts) during ~290 of the part's ticks, in stretches: 6575, 6603–6623, 7071–7113, and
  most of 7404–7708. The flock never overflows. A float remake gets the intended lighting; to match the capture,
  emulate the int32 wrap of the three-product sums.
- Painter's sort: buckets 1023 down to 0 are drawn (far to near), each bucket LIFO. With shift 3 everything with
  (Z0+Z1+Z2) >= ~9390 (mean depth > ~3130) lands in bucket 1023 unsorted; the teal plane (nose ~2600 deep, tail
  ~1800) normally stays below that. A remake should use a depth buffer.

### 6.4 Draw — 0x43df (per frame), mode [0x1ea94] = 0

```c
for (b = 1023; b >= 0; b--) for (face in bucket[b], last pushed first) {
    p = (sx >> 5, sy >> 5) for the 3 vertices;               // integer pixels (floor)
    fill_triangle(p, face.colour, backbuf);                  // 0x1a87 edges + 0x1b10 spans: flat colour
    e = face.flags;                                          // static (bits 3..5) | dynamic (bits 0..2)
    if (e & 0x09) pencil_line(p0, p1);  if (e & 0x12) pencil_line(p1, p2);  if (e & 0x24) pencil_line(p2, p0);
}
```
Outline rule: an edge is outlined when it is static-flagged (data flag, or crease >= 81 deg, or twin edge) or when
the face across it is hidden this frame (silhouette). Lines are drawn right after their face, so later (nearer)
faces cover them.

Pencil line 0x18b7 (x0,y0)-(x1,y1) (shared with the sketch parts):
```c
J0 = jitter + (((x0 * y0) + y0) & 0x1ff);   J1 = jitter + (((x1 * y1) + y1) & 0x1ff);   // position hash
S  = stroke + ((x0 + y0 + x1 + y1) & 0xff);                                               // same for all 3 strokes
for (k = 0; k < 3; k++) {                       // 3 strokes, endpoints jittered by -3..2 px (mostly -1/0)
    y1' = y1 + *J1++;  x1' = x1 + *J1++;  y0' = y0 + *J0++;  x0' = x0 + *J0++;
    line_0x1612(x0', y0', x1', y1', S);
}
// 0x1612: DDA along the major axis (16.16 slope from 65536/n), 2 pixels per step across the minor axis
// ((x,y),(x+1,y) for steep lines, (x,y),(x,y+1) for flat ones), each pixel darkened in place:
//     pix = shade[S[i++]][pix]   with S in 26..31: grey c -> c - 2*(32-S) (2..12 entries darker),
//                                group colours -> 1..6 entries darker; overlapping strokes darken repeatedly.
```
The jitter depends only on the endpoint pixel positions, so the outline "boils" as the plane moves (that is the
original's look, not noise per frame).

### 6.5 Shortcuts for a high-resolution remake

- Vertex positions are snapped to integer pixels (sx >> 5) for both polygons and lines; 1/Z by integer division
  with a truncated Z. Use float sub-pixel projection (focal length 224 at 320x200, scale with the resolution).
- Depth: bucket painter's sort (with the clamping above) -> use a depth buffer (two-sided faces + back-face culling
  as in the original: draw the face whose winding is front-facing).
- Pencil outline: 3 jittered 2-pixel strokes that darken by palette steps; at high resolution scale the stroke
  width and jitter with the resolution and keep the darkening (2..12 grey steps, 1..6 steps on the canyon colours),
  multiplied up where strokes overlap.
- Light vector overflow (teal) — decide whether to reproduce it.

## 7. Verification against the captured frames

- Contact sheets of ticks 6030–7700 and 8830–10900 (scratch `sheet1.jpg`, `sheet2.jpg`) match the reading: grey
  band = peel, black horizon band, rolling walls; teal plane enters from the right around 6540–6700.
- Canyon: Python block model == emulator back buffer (0 differing pixels) at t7000 and t9500; the 0x2f24 grid model
  matches except for 1-unit rounding (and large values inside the black band) due to the x87's incremental
  float32 direction accumulation.
- Teal path: per-tick replay from the initial waves reaches [0x6479] = (8970153, 6028530) at t6100 and
  (27759069, 16514932) at t7000, history index 26 / 2, k = 900 / 0 — identical to the snapshots. This confirms the
  per-tick time base (2 phase advances + 1 path step per tick) and the 28-step pre-roll.
- Flock: per-frame replay from the RNG state above reaches the t9500 snapshot exactly after 327 complete frames.

## 8. Not determined / caveats

- The base paper texture (0x10d3) and the peel (0x2b6c) are documented by the init and scene3d scopes; here only
  their use. The jitter/stroke tables are built at init (formulas above, from the listing; values checked).
- The capture's frame rate in the flock (34.3 fps) is a choice (NOTES.md); real 1996 hardware may have differed.
- The RNG states/initial waves listed reproduce the reference capture only; on real hardware they depend on how
  many random numbers earlier frame-rate-dependent parts consumed, so any seed is "authentic".
- Whether the camera-centre bug (5.3) and the teal light overflow (6.3) were noticed by the authors is unknown;
  both are part of the remembered look (the bug only biases where the camera looks; the overflow flips the teal
  plane's shading now and then).
